# Popups

How drawn controls open popups (the pickers today; later editable combo boxes and menus). User-facing guide with presenter examples: [SkUiPicker.md](../controls/SkUiPicker.md#popups-on-your-popup-system). Overview: [Architecture.md](Architecture.md#popups).

SkiaUi does not replace navigation, so it ships no pages and no popup windows of its own. A drawn control that needs a popup (the pickers; later editable combo boxes, menus) asks the app's popup system through one abstraction, `ISkUiPopupPresenter`, which the app implements on whatever it uses: MAUI's built-in UI, CommunityToolkit's `Popup`, another popup library, a picker UI of its own, its own overlay.

- **Request.** `ShowAsync(SkUiPopupRequest, CancellationToken)`. The request carries:
  - `Anchor`: the MAUI `View` that opens the popup (the drawn picker; for Core, its `SkUiCoreHost`), from which the presenter finds the window (`Anchor.Window`) and the page to show on.
  - `PlatformAnchor`: the nearest ancestor with a platform view (the surface root). Drawn views have no handler, so presenters that place a popup relative to a view use this one with an offset.
  - `AnchorBounds`: the anchor's rectangle in window coordinates, and relative to `PlatformAnchor`, computed by SkiaUi through drawn offsets, transforms, scrolling and clips (as the semantics tree computes accessibility bounds), with the window's safe area.
  - `Placement`: `Anchored` (below the anchor, above when it fits better, start-aligned and mirrored in RTL, at least the anchor's width), `Window` (aligned in the window by `HorizontalOptions` / `VerticalOptions`: a centered dialog or a bottom sheet), `Absolute` (a window rectangle from the app) or `BottomPane` (docked to the window's bottom edge, edge to edge, as iOS's picker). The space on each side of the anchor is precomputed, so a presenter flips without measuring. An anchored popup is cut down to the room beside its anchor, but not below a minimum height: below that it moves over the anchor instead. The minimum is a few rows (48) for a list, which scrolls; the calendar and wheel popups keep their whole height, because they neither scroll nor shrink; a picker of the app's own sets its body's minimum (`SkUiPickerPopupContent.MinimumHeight`).
  - Size: `PreferredSize` (the content measured), `MaximumSize` (the window's safe area minus margins, `MaxPopupHeight`).
  - The window: its size is measured from the surface's platform view (its `UIWindow` on iOS and Mac Catalyst, the root of its Android window, its WinUI `XamlRoot`), and MAUI's `Window.Width` / `Height` only where that is not available, so a custom window handler that never reports the frame to MAUI still keeps popups inside the window. A window of unknown size writes one `Trace` line when a popup opens; popups are then placed around the anchor without being kept inside it.
  - Frame: `CornerRadius` and `Shadow` from the look (`GetPopupCornerRadius`, `GetPopupShadow`, per placement). The drawn content is clipped to the corners; the shadow falls outside it, so the presenter's container draws it with the same corners.
  - `Content`: a ready MAUI `View`, a drawn surface (`SkUiContentView`) with the list, which any popup system hosts like any other view. A presenter that shows its own UI instead reads the typed request (`SkUiListPopupRequest`: item texts, selected index, title) and completes it with its choice.
- **Lifetime.** `ShowAsync` completes when the popup is gone. The content completes the request with a result (an item chosen); the presenter completes it with none when the user dismisses it (a tap outside, Back, Escape: the drawn content takes keyboard focus when shown, on Windows once its surface is loaded); the control cancels the token when the popup must close (`IsOpen = false`, the picker unfocused, disabled, hidden or removed, the anchor scrolled or the window resized). One popup per control; the request, its content and the presenter keep no reference to the control after completion.
- **Registration.** App-wide (`SkUiPopups.Presenter`, also settable from `UseSkiaUi(options => options.PopupPresenter = …)`), overridable per control (`PopupPresenter`). With none registered, pickers fall back to MAUI's own `DisplayActionSheetAsync` on the anchor's page (`SkUiActionSheetPopupPresenter`: centered, plain item texts; MAUI's UI, not SkiaUi's) and write one `Trace` line.
- **Closing.** The token passed to `ShowAsync` is the request's `CloseRequested`: the content's choice (`Complete`) and the control's close both cancel it, so a presenter has one rule (close on cancellation). The request holds the anchor, surface, page and window weakly and drops the content when it completes; a picker also closes its popup when its surface is torn down, so a presenter's popup still open after its page went keeps nothing alive. Presenters shown in the docs: CommunityToolkit (compiled, in the samples app and the demo), MAUI's action sheet (built in), a popup control of the app's (a sketch), a navigation service of the app's with a popup stack (open, close, bring to front).
- **Presenters are not in the library.** The library takes no popup dependency. Integrations ship as their own packages (below); other presenters are shown in the docs. The samples app and the control docs carry presenters for MAUI's action sheet, CommunityToolkit's `Popup` (the content placed in the toolkit's overlay by alignment and margins, since toolkit v2 has no anchor); [Migration.md](../Migration.md) and the migration skills show how to plug in the app's own.
- **Native over drawn.** The popup is a window-level platform view of the app's popup system, so it covers hosted native controls without overlay masks.

## Integration packages

`SkiaUi.Maui` depends on MAUI and SkiaSharp only. Integrations with other libraries are packages of their own, released with it (same version, one changelog) and built on its **public API** only (no `InternalsVisibleTo`), so they cannot couple to internals and show what app authors can build themselves:

- **SkiaUi.Maui.CommunityToolkit** (`MauiSkiaUi.CommunityToolkit/`): the popup presenter on the toolkit's `Popup`. Since 1.10 also the drawn counterparts of the toolkit's layouts on its public layout managers, as `SkUiFlexLayout` runs MAUI's `FlexLayoutManager`: [`SkUiDockLayout`](../controls/SkUiDockLayout.md) (`DockLayoutManager`) and [`SkUiUniformItemsLayout`](../controls/SkUiUniformItemsLayout.md) (`UniformItemsLayoutManager`), through `SkUiLayout`'s protected `AffectsChildLayout` (a child's `DockLayout.DockPosition` re-measures the layout) and `OnChildrenChanged`.
- A package per further popup library only if asked for; until then, a docs sketch.

## A popup of your own view

`SkUiPopups.ShowContentAsync(anchor, content, preferredSize)` shows any drawn view in the window through the same presenter, under the same contract: placed by the look's popup margin inside the safe area, closed by its request's `Cancel`, and it returns `false` when no presenter is registered. The Markdown view's `AllowImageZoom` uses it.

## Pickers of your own

Since 1.12 a picker derived from outside the library (`SkUiPickerBase.CreatePopupContent`, or `SkUiValuePicker<T>.CreateValueContent`) supplies an `SkUiPickerPopupContent`. The popup session asks the picker for it first, then the built-in picker's own content factory, then the list. The internal `SkUiCustomPopup` hosts the content's body in the same chrome as the built-in popups (`SkUiPopupParts`: title, the app's header and footer, buttons, the bottom pane's toolbar) and implements `ISkUiPickerPopupContent`, so placement, sizing, closing and focus are the session's as for every picker.

The request is an `SkUiCustomPopupRequest` (`Accept` runs the content's `OnAccepted`, `Clear` clears the picker); a value picker's content creates `SkUiValuePopupRequest<T>`, which holds the draft for both the drawn body and a presenter's own UI. The host holds the picker weakly and lets go of the content when the popup has gone. Guide: [CustomPickers.md](../controls/CustomPickers.md).
