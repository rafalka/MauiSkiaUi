# Drawn text input (Phase D, FR-16)

`SkUiEntry` / `SkUiEditor` (and their Core twins) draw their text, caret and selection with SkiaSharp. The platform still owns the keyboard, input methods (IME composition), autocorrect, dictation, the clipboard and autofill; SkiaUi drives them through a **proxy** per surface. This document records the proxy decision (D0) and how the pieces fit; the plan is in [ImplementationPlan.md](ImplementationPlan.md#phase-d--drawn-text-input-fr-16-amended).

## The pieces

| Piece | Where | What it does |
| --- | --- | --- |
| Editing engine | `SkUiTextEditor` (`Helpers/SkUiTextEditor.cs`) | The text, the selection (an anchor and the caret), the input method's composition (marked text), undo / redo, `MaxLength`, read-only, single-line, `TextTransform`. Caret movement by graphemes, words and lines. No drawing, no platform: headless tests drive it directly |
| Caret stops | `SkUiTextBoundaries` | Grapheme clusters (`StringInfo`), words (letters / digits / marks / connectors; each CJK ideograph or kana its own word; punctuation runs; white space), paragraphs. No allocations |
| Edit layout | `SkUiTextEditLayout` | Lines of editable text on the shared shaping engine (`SkUiShaping`: Latin fast path, HarfBuzz, bidi, fallback fonts), keeping what a label's layout drops: each line's text range and where each code unit sits (`SkUiShaping.CaretEdges`). Carets, hit-testing and selection boxes follow clusters and bidi runs. Paragraphs are kept by content: an edit re-shapes only the paragraphs it changed |
| Input formatters | `SkUiTextInputFormatter` (`TextInput/SkUiTextInputFormatter.cs`, D9) | Rewrite or refuse the user's edits before the editor applies them: filtering, length caps, masks, or the app's own |
| Field model | `SkUiTextFieldModel` (`TextInput/`, D3) | The control's state shared by both layers: drawing (chrome through the look, text, selection, composition underline, caret), scrolling inside the field, keys, pointer selection, and the input client the proxy talks to |
| Input proxy | `ISkUiTextInputProxy`, one per surface, set by `SkUiViewHandler` (`TextInput/SkUiTextInput.*.cs`, D2) | Attaches the focused field to the platform's text input (see below); shows / hides the soft keyboard; reports caret and composition rectangles |

## Proxy decision (D0)

The plan offered two models per platform: implement the platform's text input protocol on the surface, or drive a hidden native text view and mirror it (Uno's Skia runtime on Apple). The choice per platform:

| Platform | Model | Why |
| --- | --- | --- |
| Android | **`InputConnection` on the surface's container** (`OnCreateInputConnection`), a `BaseInputConnection` over an `Editable` mirror of the field | Android's own `BaseInputConnection` implements the protocol's edge cases (composing spans, `deleteSurroundingText` in code points, `setComposingRegion`, batch edits) on an `Editable`; SkiaUi mirrors the `Editable` to the editor after each batch (one diff, one edit) and pushes app and key changes back with `updateSelection` / `restartInput`. Flutter's `InputConnectionAdaptor` and Uno's Skia `TextInputConnection` use this model with Gboard, Samsung, SwiftKey and CJK keyboards. The container is already the focused view for drawn keyboard focus, which `showSoftInput` requires |
| iOS, Mac Catalyst | **A hidden `UITextInput` view** (a child of the surface's container, nearly transparent: alpha 0.02, so UIKit still places the candidate bar, dictation and autofill from its frame; no touches) over the editor itself, no mirror | `UITextInput` asks for geometry (`caretRectForPosition`, `firstRectForRange`, `selectionRectsForRange`, `closestPositionToPoint`), which the edit layout answers exactly: marked text, the candidate bar, dictation placeholders and the loupe sit on the drawn text. A hidden `UITextField` (Uno) would lay the text out with UIKit's own engine, so marked-text and candidate positions would only approximate the drawn ones. Flutter's `FlutterTextInputView` is the reference; autofill uses `textContentType` on the same view |
| Windows | **A hidden WinUI `TextBox`** in the container, mirrored | `CoreTextEditContext` needs `CoreTextServicesManager.GetForCurrentView()`, which depends on a `CoreWindow` that WinUI 3 desktop apps do not have; a `TextBox` gets the IME (TSF), the touch keyboard, dictation and Windows' input scopes in every host. SkiaUi handles navigation and shortcut keys itself (the `TextBox` sees character and IME input only), mirrors its text changes into the editor as one diff per change, and takes its composition from `TextCompositionStarted` / `Changed` / `Ended`. Avalonia's `WinUITextInputMethod` (CoreTextEditContext) is the reference for the other model, should a CoreWindow host be needed |

Common to all: one client per focused field, attached when it takes keyboard focus and detached when it loses it; the drawn field stays the source of truth for drawing; edits from the platform reach the editor as `Replace` / `SetComposingText` / `FinishComposing` calls, edits from keys and the app reach the platform as one state update. Hardware keys go through the focus manager (`ISkUiKeyHandler`) like every drawn control's keys; typed characters arrive through the input method on every platform (so hardware-keyboard IMEs work).

What the device runs must measure for each model (the plan's D0 list): CJK and Korean composition, autocorrect and suggestions (accepting one replaces the word), dictation, autofill and password managers, the edit menu, and the soft keyboard showing / hiding with focus.

## Editing engine (D1)

- **Text and selection.** `Anchor` and `Caret` (the moving end); `SelectionStart` / `SelectionEnd` / `SelectionLength` as MAUI's `CursorPosition` / `SelectionLength` read them. `CaretUpstream` keeps the caret at the end of a wrapped line (after End, or a click past the line's end) instead of the start of the next.
- **Edits.** `Replace(start, end, text, kind)` is the one edit: read-only refuses it, a single-line field turns line breaks into spaces (a multiline one normalizes `\r\n` / `\r`), `TextTransform` applies, and what would pass `MaxLength` is cut (never inside a surrogate pair). `InsertText` replaces the composition, else the selection. Backspace / Delete remove the selection, else a grapheme (Backspace peels the last mark off a letter and removes emoji whole) or a word.
- **Composition.** `SetComposingText` replaces the composition (or the selection) with marked text; `SetComposingRegion` marks committed text (reconversion); `FinishComposing` commits; `CancelComposition` removes it. Edits before the composition move it; an edit across it ends it.
- **Undo.** Steps of typing join until a new word starts (word-by-word undo, as Windows and Android fields); Backspace / Delete runs join; a whole composition is one step; paste, cut and replacements are steps of their own; a caret move ends the step. Undo restores the selection the step started with. `SetText` (the app) clears the history. At most 100 steps.
- **Movement.** Left / Right by grapheme (swapped in right-to-left lines), words (`WordRight` goes to the next word's start on Windows / Android, to the word's end on Apple), line start / end, up / down / page with the kept x (`GoalX`), document start / end. Lines come from the layout through `ISkUiTextEditGeometry`; without one, lines are paragraphs.
- **Batches.** `BeginBatch` / `EndBatch` (an input method's batch edit) report one text change and one selection change to the owner.

## Edit layout (D1)

- **Lines.** A paragraph per `\n`. Single-line text is one unwrapped line; multiline text wraps at a width (words, then characters, as labels: `SkUiTextLayout.Wrap`). A wrapped line owns its trailing spaces (they hang past its drawn width, so a caret after them stays on the line); the `\n` belongs to no line.
- **Caret edges.** `SkUiShaping.BuildLine` optionally fills `CaretEdges`: each code unit's left and right x and bidi level, from the glyphs' positions and clusters in visual order. A ligature's width is split between its graphemes; the later code units of a grapheme share its edges. The simple path takes the edges from its advances.
- **Caret x.** The leading edge of the character after the caret (its left in a left-to-right run, its right in a right-to-left run); at a line's end, the trailing edge of the last character. One caret per position (no split caret at bidi boundaries).
- **Hit-testing.** The line by y, then the nearest character by x: before or after it by which half was hit and its direction.
- **Selection.** One box per visual stretch of the range on each line (a range across a bidi boundary can be two boxes), plus a narrow box for a selected line break.
- **Incremental.** `Update` compares the new paragraphs with the kept ones from both ends and lays out only the changed ones; kept lines are re-indexed and moved. The same text, style and width do nothing.
- **Ownership.** The layout owns its lines' blobs; replaced ones are disposed (recorded pictures keep their own references), and `Release` disposes them all when the field's drawing resources are released.

Left open in D1: a split caret at bidi boundaries, visual (rather than logical) Left / Right through mixed-direction lines, allocation-free re-shaping of an edited paragraph (one paragraph is shaped per keystroke; its line arrays and blob are new).

## Platform proxies (D2)

The contract (`TextInput/SkUiTextInput.cs`): the focused field's model is an `ISkUiTextInputClient` (the editor, `SkUiTextInputOptions` for the keyboard, edits, return and edit actions, geometry in surface DIPs); the surface's `ISkUiTextInputProxy` is told `Attach` / `Detach`, `ShowKeyboard` / `HideKeyboard`, `StateChanged` (text or selection changed by keys, the pointer or the app), `OptionsChanged`, `GeometryChanged` and `ShowEditMenu` / `HideEditMenu`. The focus manager (`SkUiFocusManager.TextInput`) attaches the field that takes focus (`ISkUiTextInputNode.WantsTextInput`) and detaches the one that loses it; nothing else talks to the proxy. A surface without a proxy (headless tests, software surfaces) still edits: typed characters reach the field as keys.

- **Android** (`SkUiAndroidTextInput`, `SkUiInputConnection`). The overlay container is a text editor while a field is attached (`OnCheckIsTextEditor`, `OnCreateInputConnection`); `Attach` restarts input and shows the keyboard (posted, once the container has window focus). `Configure(EditorInfo)` maps the options: input class and variation (numeric with signed / decimal, phone, email, URI, chat's short message, multiline, a numeric password), `ImeAction` from `ReturnType` (search, go, next, send, done; none in multiline), no suggestions / no autocorrect, caps from `TextTransform` and `Keyboard` flags, `NoExtractUi`. The connection is a `BaseInputConnection` over a `SpannableStringBuilder` mirror: every IME call runs inside a batch, and when the outermost batch ends the mirror is diffed into the field (common prefix and suffix: one `Replace`), then its composing span becomes the composition and its selection the field's. Field changes from elsewhere are pushed back into the mirror and reported (`UpdateSelection`, extracted text when monitored, `CursorAnchorInfo` with the caret and composing character bounds when the IME asked for cursor updates). `Detach` hides the keyboard unless the next focused node takes text input too. The edit menu is a floating `ActionMode` (`ActionMode.Callback2` with the selection's rectangle). Some keyboards send Enter and Backspace as key events (`sendKeyEvent`: Samsung Keyboard always does in a multiline field); they reach the field through the container's `DispatchKeyEvent` like hardware keys, and a key that types (Enter, Space, a character) keeps a composition the keyboard left as typed text instead of replacing it, as a native `EditText` does.
- **iOS / Mac Catalyst** (`SkUiAppleTextInput`, `SkUiTextInputView`). The view implements `UITextInput` directly over the editor (positions are `SkUiTextPosition` indexes, ranges `SkUiTextRange`), answering geometry from the edit layout; marked text maps to the composition. The container hands first responder to it (`HandTextInput`) and takes it back on detach (`TakeTextInputBack`), so the container's own `ResignFirstResponder` ignores that handover; a field attached while the view is already first responder reloads input views instead. Field changes call the input delegate's `selectionWillChange` / `textWillChange` pairs. Traits (`keyboardType`, `returnKeyType`, autocapitalization, autocorrection, spell checking, secure entry, `textContentType` from `AutofillHint`, smart quotes and dashes off for passwords) are exported properties. Hardware keys arrive in `PressesBegan`: navigation keys and ⌘ / Ctrl + letter go to the focus manager unless the input method is composing; characters come through `insertText`. `insertText("\n")` in a single-line field is Return. The edit menu is `UIEditMenuInteraction` (iOS 16+), else `UIMenuController`, with the standard actions' `CanPerform`. It is preferred above the selection (below when there is no room) and never over the text: the view keeps its delegate (UIKit holds it weakly; once collected, the target rect was ignored and the menu sat on the text), and the target rect is given in the container's coordinates, which is how UIKit places it (in the view's own coordinates, as documented, it landed off by the view's position; checked on iOS 26, Mac Catalyst not yet). UIKit answers the field's own `selectionDidChange` with a `setSelectedTextRange` of the keyboard's (a double-tapped word collapsed to its end); selection sets that arrive while the view is notifying are ignored. Keyboard frame notifications give the focus manager the keyboard's top.
- **Windows** (`SkUiWindowsTextInput`). A `TextBox` (opacity 0, clipped to nothing so clicks reach the surface) in the container, placed over the field's text bounds, takes focus on attach. `Configure` sets `InputScope` (number, telephone, email, URL, chat, search, password; for `ReturnType.Search` the search scope goes first, as MAUI's entry does, since WinUI uses the first name: the touch keyboard's Return key becomes a search key, the only Return type Windows shows), `AcceptsReturn`, spell checking, prediction and `CharacterCasing`. The field's state is copied into the box; the box's `TextChanged` is diffed back into the field, and `TextCompositionStarted` / `Changed` / `Ended` mark and commit the composition. `PreviewKeyDown` routes navigation and Ctrl + letter keys to the focus manager, so editing commands behave as on the other platforms. The edit menu is a `CommandBarFlyout` as a native text box's (cut, copy and paste as icons when they can run, select all under "more"; `SkUiStrings`' texts). The box's peer reports focus as the field's element (`EventsSource`), so Narrator announces the drawn field. WinUI behaviors the proxy works around (found running it on Windows 11):
  - **No `IsHitTestVisible = false`:** a text box that is not hit-test visible raises `TextChanging` but never `TextChanged` or `SelectionChanged`, so typed text would never reach the field. An empty `Clip` keeps clicks off it instead.
  - **`TextChanged` and `SelectionChanged` come late** (from a deferred XAML message), after the copy that caused them has finished: the box's own echo of the field's state is recognized by comparing (equal text, the same selection range) rather than by the copy guard alone, so it neither ends an undo step nor turns a backward selection around.
  - **Line breaks are `\r` in the box:** it turns a `\n` copied in into `\r`, so the field's text goes in with each `\n` as `\r` and comes out with each `\r` as `\n` (one character for one: indexes match). Copied as is, the box's `\r` came back as an edit, the field turned it into `\n` and copied it in again, without end: the app spun after the first Return, and each round re-laid out the whole text and added an undo step.
  - **No focus or visibility change inside `LosingFocus`:** WinUI fails fast (`0x802B0020`, a stowed exception) on one. The field is unfocused, and the box collapsed, one dispatcher turn later, and only if focus did not come back to the box or the container.
  - **The touch keyboard and the edit menu:** a menu taking focus from the box hides the touch keyboard, so the menu a touch gesture opens (`ShowEditMenu`'s `byTouch`: a double tap, a long press, a handle) shows `Transient` above the selection without taking focus, as a text box's selection flyout. A tap on one of its buttons still hides the keyboard (Windows exempts only a text box's own flyout), so after the action the box asks for it again (`InputPane.TryShow` through `InputPaneInterop`) when it was up. A right click's menu opens at the point in `Standard` mode and takes focus (keyboard navigation), as a text box's context flyout.
  - **The edit menu takes focus:** focus moving into an open right-click menu keeps the field focused; when the menu closes (an item, Escape, or a click outside, after which WinUI focuses some other control) the box takes focus back, as a native text box keeps it.
  - **A password field's box holds a mask, not the password:** UI Automation reads a `TextBox`'s text through its windowless RichEdit (the box's raw view, and its peer's patterns fall back to the RichEdit's), so `AccessibilityView.Raw` and a peer without patterns do not hide it. The box holds one `●` per UTF-16 unit of the field's text (as MAUI's password text box), so indexes still match, and its peer reports `IsPassword` (as a `PasswordBox`'s). A diff cannot place an edit in a run of one repeated character: what the box typed is taken from the field's selection to the box's caret (a typed `●` included), a deletion from the input method from the caret. Showing the password copies the text in again.
  - A press does not focus a text field before its gesture runs (`SkUiFocusManager.PointerPressFocuses` skips fields): the field focuses on the click or tap, so the first tap on an unfocused field does not count as a tap on the caret of a focused one (which opens the edit menu).

## Text fields (D3)

`SkUiTextFieldModel` is the field's state and behavior on both layers; `SkUiInputView` / `SkUiCoreInputView` (and the entry, editor and search bar on them) are facades that copy their properties into it and implement `ISkUiTextFieldOwner` (size, direction, focus, invalidation, `TextEdited` / `SelectionEdited` / `Completed` back to the control).

- **Drawing.** The look draws the chrome (`DrawTextField`: underline, outline or filled by `DefaultSkUiLook.TextFieldStyle`, with the `FieldFocus` transition), then inside the text area (`TextFieldPadding`, minus the clear button or the search icon): the selection boxes, the text or placeholder, the composition underline, and on touch the selection handles. A password draws one bullet per grapheme (`ToDisplay` / `ToSource` map indexes between bullets and text).
- **The control's text.** `SetText` (the app set `Text`) shows it cut to `MaxLength` and transformed; `SetTransform` (a new `TextTransform`) transforms the text already there, keeping the caret. Either returns the shown text when it differs, and the control raises its own `TextChanged`, then sets `Text` to the shown text (a second change; a two-way binding gets it), as MAUI's native fields push back what they show.
- **Caret.** Not recorded: `GetCaretDrawable` returns a `SkUiCaretDrawable` (a rectangle and a clip) in the node's render props, so moving or blinking the caret is a props change. The blink is a UI timer (`CaretBlinkInterval`, 500 ms) that toggles it, rather than a render-thread animation that would draw every frame; typing restarts it solid.
- **Scrolling.** A single line scrolls horizontally to keep the caret in view (`KeepCaretInView`); the editor scrolls vertically. Wheel input goes to the field (`ISkUiWheelHandler`) while it can scroll, else to the scrollers around it.
- **Keys.** `OnKeyDown` maps keys and modifiers per platform (⌘ / ⌥ on Apple, Ctrl elsewhere) to editor moves, deletions, clipboard and undo shortcuts, Return and Tab.
- **Return.** Multiline: a line break. Otherwise `Completed`, then `ReturnType.Next` moves focus; a search bar on a phone gives focus up; iOS (not Mac Catalyst) gives focus up; Android hides the keyboard (MAUI's native fields' behavior).

## Selection UI (D4)

`SkUiTextFieldGestures` is the field's arena member. Mouse: it claims on press (one, two or three clicks: caret, word, all; a press counts on from the last tap or click when it comes within `DoubleTapTimeout` of that release and `DoubleTapSlop` of it, as Android's double tap: measured from press to press, a finger's double tap often took longer than the timeout), drags extend the selection, Shift-click extends it, the secondary button opens the edit menu at the pointer (pointer buttons reach recognizers through `SkUiTouchEvent.Buttons` → `SkUiPointer.Buttons`, from Android's `ButtonState`, `UIEvent.ButtonMask` and SkiaSharp's mouse button). Touch: a tap places the caret (on the caret it toggles the menu; when unfocused it focuses first), a double tap selects a word and shows the menu, a long press claims after `LongPressDuration` and selects the word, extending by words while dragged and showing the menu when lifted. A touch on a handle (`TextSelectionHandleTouchRadius`) claims and drags that end. Other drags resign, so the page scrolls (an editor that can scroll that way scrolls itself). Handles are drawn by the look (`DrawTextSelectionHandle`) inside the field's clip; the menu is the platform's (`ShowEditMenu` with the selection's rectangle), hidden on edits, other selection changes, handle drags and focus loss. Clipboard actions go through `SkUiTextClipboard` (MAUI `Clipboard`; replaceable in tests); paste is asynchronous.

## Editor (D5)

The same model with `IsMultiline`: wrapping at the text area's width, Return inserts `\n`, Up / Down / Page keep the x, the text area scrolls vertically to keep the caret in view (also while the editor grows). `AutoSize="TextChanges"` re-measures on each text change; fields are at least the look's `DefaultTextFieldMinimumHeight` unless `MinimumHeightRequest` is set; otherwise the editor keeps its size and scrolls. `VerticalTextAlignment` defaults to `Start` for the editor (`Center` for the entry). `Completed` is raised on unfocus, as MAUI's editor.

## Integration (D6)

- **Keyboard avoidance.** The proxy reports the keyboard's top in surface DIPs (`SkUiFocusManager.SetKeyboardTop`): iOS from the keyboard frame notifications; Android from the container's size (adjust-resize) and MAUI's default adjust-pan, which uses the container's `GetFocusedRect` (the field's caret). `RevealFocusedField` then sets `SkUiScrollController.KeyboardInset` on every drawn vertical scroller around the field (`ISkUiScrollHost.KeyboardInset`: `SkUiScrollView` and `SkUiCoreScrollView`), by the part of its viewport the keyboard covers (added to its end inset, so the content can scroll that far), and scrolls the field into the band above the keyboard from the innermost scroller out: an outer scroller scrolls only once the one inside it settled with the field still covered (a short scroller nested in a taller one), and the native reveal (`RequestNativeReveal`) runs when none could show it. The insets go when the keyboard does or focus moves to a field outside those scrollers. A field outside drawn scrollers asks native scrollers around the surface (the page's own soft-input mode applies).
- **Following the field.** After each committed frame (`SkUiFrameRenderer` → `FocusManager.OnFrameCommitted`) the focus manager compares the focused field's bounds with the last ones and tells the proxy `GeometryChanged`: the Windows box moves, Android's cursor anchor and iOS's geometry queries follow scrolling and animations.
- **Focus.** Text fields take focus with accessibility off and when they are not tab stops (`CanFocus`); Tab, `ReturnType.Next` and taps move between them with the keyboard kept up. A field draws its focus in the chrome (`ShowsFocusRing` off). Focus loss from the platform (another native view, the window) detaches the field.
- **Screen readers.** `SkUiSemanticsRole.TextField` with `SkUiSemanticsTextField` (selection, password, read-only, multiline) on the info and node; the placeholder is the name and the text (bullets for a password) the value. Android: `EditText` with `Editable`, `Password`, `MultiLine`, the text selection, and the set-text and set-selection actions (`SkUiSemanticsOwner.SetText` / `SetSelection`). Windows: control type Edit with a writable `IValueProvider`, `IsPassword` for a password; the hidden text box reports its focus as the field's element. Not on Windows yet: the Text pattern (Narrator does not read the selected text, which it reads in a native text box), and UI Automation's focused element (`GetFocusedElement`) is the surface rather than the field (WinUI asks the box's RichEdit for it, past `EventsSource`). iOS: the value (VoiceOver's text navigation by character and word is open).

## Stepper (D7)

`SkUiStepperModel` (both layers, every value type): it asks its control through `ISkUiStepperOwner` whether it can step, to step, and for the screen reader's range and text, so the value stays the control's: `SkUiStepper` / `SkUiCoreStepper` on `double` with MAUI's coercion, `SkUiStepper<T>` / `SkUiCoreStepper<T>` on any `INumber<T>, IMinMaxValue<T>` through `SkUiStepperMath<T>` (MAUI's rounding for binary floating point only, steps clamped before they could overflow). What the steppers share (orientation, texts, fonts, shape, keys, focus) is `SkUiStepperBase` / `SkUiCoreStepperBase`, with `private protected` abstract value members so only SkiaUi derives from them. The engine draws the − and + segments from the look (`StepperButtonSize`, `DrawStepper` with `SkUiStepperPaint`), side by side (− at the start side) or stacked (+ on top) by `Orientation`, each half of the arranged size. `DecrementText` / `IncrementText` (with the font group) replace a glyph with one centered line on an `SkUiTextLayout` per button (made on first use, its blobs released with the drawing resources); the look is told through `SkUiStepperPaint.HasDecrementText` / `HasIncrementText` and the control draws the text over it, and a text larger than the look's button grows both buttons. `CornerRadius` (the look's `StepperCornerRadius` until set), `BorderWidth` and `BorderColor` reach the look as `SkUiStepperPaint` fields; the texts are inset by the outline's width. Buttons only, as MAUI's: no text field, so it is not a text input node and focusing it shows no keyboard. `SkUiStepperGestures`: a mouse press steps at once and repeats (`StepperRepeatDelay`, `StepperRepeatInterval`) while held; a touch steps when lifted or repeats after a long press, so a drag across the stepper can still scroll. Up / Down step; the focus manager's range keys do the rest. Screen readers see a slider with a range.

## Search bar and cells (D8)

`SkUiSearchBar` is an entry with `IsSearch`: the look's pill (`DrawSearchField`) with a magnifier (`SearchIconWidth`), the clear button shown whenever it has text, focused or not (`CancelButtonColor`), the search return key / input scope, and `SearchCommand` / `SearchButtonPressed` on Return. Fields in collection view item templates need nothing special: the model releases its layout with the cell's drawing resources, and a recycled cell's field takes the new item's text through its binding like any other control (no dedicated sample yet).

## Input formatters (D9)

`InputFormatters` on every drawn field (both layers; the editor's `Formatters` holds the control's list): an ordered list of `SkUiTextInputFormatter`s, Flutter's `TextInputFormatter` model. Chosen over a per-edit hook (start, end, inserted) because masks and numbers rewrite the whole text and place the caret, which an insertion-only hook cannot express.

- **Where.** `SkUiTextEditor.Replace`, the one edit every input path goes through (keys, the platform proxies' diffs, paste, cut, Backspace / Delete, a screen reader's set-text). After the editor's own cleaning (line breaks, `TextTransform`) and `MaxLength` cut, the proposed text (the old text with the range replaced, the caret after the insertion) goes through the formatters in order, each getting the value before the edit and the previous one's result (`SkUiTextEditValue`: text, selection). The result, clamped, becomes one edit: `Diff(old, result)` is recorded as one undo step of the edit's kind (so typing still joins word by word), the selection goes where the formatters put it. A result equal to the old text refuses the edit but still moves the caret (a typed separator stepping over the one already there).
- **Composition.** Marked text is not formatted while composed (`SetComposingText`, `CancelComposition`, and edits while a composition exists skip the formatters): the input method must see its own text. Committing (`InsertText` over the composition, `FinishComposing`) formats the committed text as an edit joining the composition's undo step.
- **Not formatted.** Undo / redo (they restore states the formatters produced), and `SetText` (the app). `FormatsAssignedText` (default off, as Flutter) formats text the app sets in the field model, as if pasted into an empty field, and the control's `Text` follows the result (as for `MaxLength` and `TextTransform`); turning it on formats the text already there. Changing the formatters always formats the text already in the field (as `TextTransform` does when it changes), so the field never holds text its formatters would refuse.
- **`MaxLength`.** Applied to the insertion before the formatters; a result longer than both `MaxLength` and the old text (a mask's literals) is cut.
- **Proxies.** Android diffs its mirror into the field and pushes back whatever the field did differently; Windows copies the field back into its `TextBox` when the text or (new with D9) the selection differs; iOS answers text and geometry from the field. iOS is not told (`textWillChange`) when a formatter changes text UIKit inserted, as with `MaxLength` today.
- **Built in.** `SkUiFilteringFormatter` (regex via `EnumerateMatches`, or a `Rune` predicate; allow or deny, with a replacement; the caret maps through the removed stretches), `SkUiLengthLimitingFormatter` (cuts what the edit inserts past the cap: whole graphemes, or up to the last digit that fits; text already over the cap is not cut but cannot grow), `SkUiMaskFormatter` (.NET `MaskedTextProvider`'s required placeholders `0`, `L`, `A`, `&` and `\` escapes; walks the new text against the mask, inserting literals only in front of a character that fills a placeholder, keeping typed literals, dropping what fits nowhere; a deletion that only removed literals removes the input character beyond them; a deletion drops literals left at the end).

Left open: device checks of formatted input with suggestions, autocorrect and CJK commits.

## Moving the caret by touch, magnifier (D15)

- **Insertion handle** (where `SkUiLook.ShowsTextInsertionHandle`: Android by default). A touch tap that places the caret (or taps it) shows a handle under it, drawn by the look (`DrawTextInsertionHandle` inside `GetTextInsertionHandleBounds`: a drop hanging from the caret). It goes after `TextInsertionHandleTimeout` (4 s) unused, when typing, selecting, using a mouse or losing focus. A finger on it that moves past the touch slop drags the caret; a tap on it is a tap on the caret (it toggles the edit menu, paste), and it counts towards a double tap: the second tap of a double tap often lands within the reach of the handle the first one showed, and still selects the word.
- **The caret itself** (elsewhere, as on iOS). A finger near the caret that moves past the touch slop drags the caret; a tap there stays a tap, so a double tap on the word under the caret still selects it.
- **Drags** keep the finger's offset to the edge it grabbed (the finger does not cover the caret), start past the slop, and keep the caret solid (no blink) while it moves.
- **Outside the field.** Handles hang below or above the text, also outside the field's rectangle: while they show, the node's render props stop clipping it to its bounds and report the room as `Overflow` (the field clips its text itself), and the pointer router offers a press to the focused text field's handles (`ISkUiTextInputNode.HitsTextHandle`) before its hit test, which is bounded by each node's rectangle. They still follow scrolling and animations on the render thread, being part of the field's own drawing.
- **Magnifier.** While a handle, the caret or a long press's selection moves, the field asks the proxy to show the platform's magnifier at the moving end (`ShowMagnifier(client, caret)` in surface DIPs; `HideMagnifier` when the finger lifts). Android: `android.widget.Magnifier` (API 28+) on the surface's container; it copies the window, where the texture-view surface is, and is refreshed two frames later since the GL thread draws the moved caret after the copy. iOS / Mac Catalyst: `UITextLoupeSession` (17+) in the container. Windows: none.

Left open in D15: handles clipped by a scrolling ancestor can still be grabbed where they are hidden; Windows has no touch magnifier.

## Numeric entry (D16, proposed)

An entry meant for numbers only, with optional − / + buttons in its chrome. Not a MAUI control: MAUI apps use an `Entry` with `Keyboard="Numeric"` and a converter, or a vendor control. Reference controls: Syncfusion `SfNumericEntry` / `SfNumericUpDown` (the open toolkit) and Telerik `RadNumericInput`. It is a composition of the entry's field engine (`SkUiTextFieldModel`), not a new editor, and keeps `SkUiStepper` (buttons only, MAUI's) as it is.

### Order: after D9 and D11

Its two hardest parts are what D9 and D11 generalize, so building it first would mean private versions of both, replaced later:

- **Filtering input is D9 (shipped).** `SkUiTextEditor.Replace` runs the field's input formatters ([Input formatters](#input-formatters-d9)); the numeric filter is one of them.
- **Buttons in the field are D11.** The clear button and the search icon are special cases in `SkUiTextFieldModel` (`Inset`, `HitsClearButton`, `MousePressed`, `Tapped`). Stepper buttons would be a third, harder one: they repeat while held, which the clear button does not.

So: D9's engine (shipped), then D11, then D16 as the acceptance case that shapes both APIs. D10 is optional (an out-of-range value shown as an error instead of clamped).

What already exists and keeps D9 / D11 small:
- **The proxies accept a field that changes an edit.** Android diffs the mirror into the field and pushes back what the field did differently (as for `MaxLength`); iOS answers geometry and text from the field itself; Windows copies the field's state back into its `TextBox`. A formatter needs no proxy work (to confirm on Windows).
- **The value math.** `SkUiStepperMath<T>`: typed steps that never overflow, MAUI's rounding for binary floating point, exact `decimal` and integers.
- **`SkUiTextFieldModel.FieldArea`.** The field can take part of the node, which fits buttons at both ends (`Split`).

Can be done before D9 / D11 without rework: the press-and-repeat handling moved out of `SkUiStepperModel` (`SkUiStepperGestures`, `Press` / `Repeat` / `Release`) into a helper both controls use; a headless parse / format engine (`SkUiNumericText<T>`) with tests; the iOS keyboard for numbers with a sign (below), which affects today's `SkUiEntry` with `Keyboard.Numeric` too.

### API

- **Controls.** `SkUiNumericEntry` on `double?` (as both vendors) and `SkUiNumericEntry<T>` with `Value` of type `T?` (`where T : struct, INumber<T>, IMinMaxValue<T>`, as `SkUiStepper<T>`; `x:TypeArguments` in compiled XAML, Native AOT), on a shared `SkUiNumericEntryBase` with `private protected` abstract value members (as the steppers); Core twins `SkUiCoreNumericEntry` / `SkUiCoreNumericEntry<T>`. The entry's members by name (`Placeholder`, fonts, alignments, `ReturnType`, `ReturnCommand`, `Completed`, `ClearButtonVisibility`, `CursorPosition`, `SelectionLength`, `IsReadOnly`, …); `Text` is read-only (the shown text).
- **Value.** `Value` (two-way), `Minimum`, `Maximum`, `Increment` (default 1), `LargeIncrement` (Page Up / Page Down; default 10 × `Increment`), `ValueChanged` with old and new value (raised synchronously, unlike Syncfusion's). `AllowNull` (default `true`): empty text is `null`; with `false`, empty text commits 0 clamped into the range.
- **Buttons.** `ButtonPlacement`: `None` (default), `End` (both at the end side), `Start`, `Split` (− at the start, + at the end); `ButtonOrientation` (`StackOrientation`): side by side or stacked. `End` / `Start` follow RTL. The four common layouts: `End` + horizontal, `End` + vertical (+ above −, a spinner), `Split` + horizontal (Telerik's − [ 5 ] +), `Split` + vertical (+ above the text, − below it; full-width bars). Syncfusion's `UpDownButtonAlignment` `Left` / `Right` / `Both` × `UpDownPlacementMode` `Inline` / `InlineVertical` map onto these. `DecrementText` / `IncrementText` with the font group, `ButtonColor`, as on the stepper; the look draws them (`DrawTextFieldStepButtons`: pressed, disabled at an end, dividers to the text).
- **Formatting.** `Format` (a .NET numeric format string: `"N2"`, `"C0"`, `"P1"`, `"0.## kg"`) and `Culture` (default the current culture). Unfocused, the field shows `Value` formatted; focused, the plain number (no group separators) with everything selected. Unlike Syncfusion, losing focus does not round `Value` to the shown digits; `MaximumDecimalDigits` (default: none for `decimal` / binary floating point, 0 for integers) is the only rounding, applied while typing and on commit.
- **Committing.** `ValueChangeMode`: `OnCompleted` (default: Return, focus loss, a button, a key step) or `OnKeystroke` (every edit that parses). Out of range is clamped on commit, never while typing (with `Minimum` 10 the user must be able to type the 1 of 15). Escape restores the last committed value. A value set by the app is clamped at once, with the stepper's rule that the asked value returns when the range widens.
- **Behavior.** `IsEditable` (default `true`; `false`: buttons and keys only, Telerik's `IsReadOnly`; MAUI's `IsReadOnly` still means nothing changes). `AutoReverse`: past `Maximum` wraps to `Minimum` and back. Held buttons repeat (`StepperRepeatDelay`, `StepperRepeatInterval`), optionally accelerating (`RepeatAcceleration`).

### Input rules (a D9 formatter)

- Digits, the culture's decimal separator (once; typing it again moves the caret after it; refused when `MaximumDecimalDigits` is 0 or `T` is an integer) and its negative sign (only when `Minimum` < 0). Both `.` and `,` from a decimal pad map to the culture's separator.
- The sign toggles wherever the caret is ("−" on `12|3` gives `-123`); the caret never goes before it. A leading separator gets a 0 (`,5` → `0,5`); leading zeros are trimmed on commit.
- Paste is cleaned (`"1 234,50 €"` → `1234,50`); text that cannot become a number after cleaning is refused.
- Integer types refuse what would overflow `T` while typing (a `byte` field refuses 256); the range is still applied only on commit.
- A composition is filtered when committed, not while composing (numeric keyboards rarely compose).

### Buttons, keys and focus

- **Buttons do not take focus.** On an unfocused field a button steps `Value` without focusing it or showing the keyboard (a phone user taps + without the keyboard covering the form). On a focused field the typed text is committed first, then stepped; focus and the keyboard stay. Touch steps on lift and repeats after a long press (a drag still scrolls), as `SkUiStepperGestures`.
- **Keys** (focused): Up / Down step, Page Up / Page Down by `LargeIncrement`, Enter commits, Escape reverts; Home / End stay caret keys. **Wheel**: steps while the field is focused (desktop).
- **Keyboard picked from the type and range** (instead of `Keyboard.Numeric`'s one mapping): a non-negative integer → Android `ClassNumber`, iOS `NumberPad`; decimals → `NumberFlagDecimal`, `DecimalPad`; a negative minimum → `NumberFlagSigned`, and on iOS `NumbersAndPunctuation` or an input accessory bar with − (Syncfusion's iPhone toolbar), since `DecimalPad` has no minus key; Windows `InputScopeNameValue.Number`. Today the iOS proxy maps `Keyboard.Numeric` to `DecimalPad` (`SkUiTextInputView.KeyboardType`), so no SkiaUi field can take a negative number on an iPhone.

### Screen readers

A text field (`SkUiSemanticsRole.TextField`, value = the shown text) with `Increment` / `Decrement` actions. To spike on devices: VoiceOver's adjustable trait and a text field do not combine cleanly (swipe up / down vs character navigation); TalkBack exposes the actions as custom actions; Narrator a `RangeValue` pattern next to `Value`.

### Later, if asked for

`IncrementCommand` / `DecrementCommand` (Telerik); a percent mode (Syncfusion `PercentDisplayMode`: `Value` 50 shown as 50 % instead of 0.5); a unit before or after the number as a D11 adornment instead of in `Format`; out-of-range shown as an error (D10) instead of clamped; expressions (`2+3*4`, WinUI `NumberBox.AcceptsExpression`); dragging on the field to change the value (design tools).

### When it ships

Control page in `docs/controls/`, a demo gallery page next to the stepper, `NumericEntryTests` / `TypedNumericEntryTests`, a migration table in [Migration.md](../Migration.md) and the migration skills: `SfNumericEntry` / `SfNumericUpDown`, `RadNumericInput`, and the `Entry` + `Keyboard="Numeric"` + converter pattern.
