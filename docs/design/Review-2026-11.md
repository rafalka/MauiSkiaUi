# SkiaUi review, November 2026: architecture, .NET 10 / 11 use and feature proposals

A review of SkiaUi at 1.12.0, done on 16 November 2026. Its findings are agreed. What follows from them is in the [roadmap](Roadmap.md) (1.14.0, planned as 1.13.0 until the calendar took that release on 17 November 2026, and the backlog), the [1.14 plan](../archive/ImplementationPlan-1.14.md) and the [review plan](ImplementationPlan-PerformanceAndControls.md) with a brief per work package. This page is a record of the review and is not updated as the work ships.

## Summary

The architecture needs no rework: the retained, two-thread pipeline is the reason SkiaUi builds a 1,000-button page 13 to 29 times faster than native MAUI and scrolls it at 60 fps ([Performance.md](../Performance.md)). The work worth doing is seven small allocation fixes and ten additions to the control set.

- **Architecture:** sound. The main cost is structural duplication between the SkUi\* and Core layers, and device verification that trails the release pace (12 minor releases in 25 days, about a dozen open device checks).
- **Language and runtime features:** the hot paths already use what C# 12 to 14 and .NET 9 to 10 offer (readonly structs, `in` parameters, static lambdas, `field`, `UnsafeAccessor`, collection expressions). Seven gaps remain, all local and small.
- **C# 15 and .NET 11:** C# 15 has no feature that reduces allocations, and shared source must stay C# 14 while SDK 10 builds the net10 line. .NET 11's gains (JIT, cached interface dispatch on iOS, CoreCLR on mobile) arrive without code changes; the device numbers in Performance.md are still .NET 10 and should be measured again.
- **Features:** the control set covers MAUI parity. What other toolkits have and SkiaUi lacks is data visualization, navigation-style containers and scroll-driven motion.

The findings come from reading the code and counting patterns across its 371 files (110,546 lines). No benchmark was run for the review, so each performance item names the scenario that has to confirm it.

## Architecture review

The design holds up, and its open risks are already named in the roadmap. Three risks were not on it: layer duplication, look extensibility for optional packages, and verification debt.

### What holds up

| Decision | Why it works | Evidence |
| --- | --- | --- |
| One surface per host, one `SKPicture` per node | No handler or platform view per control | 1,000 buttons ready in 433 ms (SkUi\*) and 271 ms (Core) against 5,633 ms native on a Galaxy S9 |
| Composite-time properties (`SkUiRenderProps`) | Scrolling, transforms, opacity, clips and shadows record nothing | No picture recorded during any scroll in the effects matrix |
| Render thread owns compositing and animations | Flings and `AnimateAsync` keep running while the UI thread is busy | 60 fps scroll on both test phones |
| MAUI's measure and arrange contract | Pages port by changing the XAML prefix; MAUI's layout managers are reused | `SkUiGrid` on `GridLayoutManager` |
| Shared engines under both layers | Text, shapes, scrolling, images and toggles are written once | Parity tests compare the layers |
| One ownership rule for native objects | The compositor disposes what is committed; nothing reaches the finalizer | `ReleaseDrawingResources`, leak scenarios run headless and on devices |
| Trim and AOT analyzers fail the build | No reflection left for MAUI internals | 20 `UnsafeAccessor` uses, no `GetMethod` or `GetProperty` |
| Headless tests on real MAUI objects | Fast feedback without a device | 2,506 tests, 69,845 lines, about 10 s |

### Risks not on the roadmap

1. **Two layers, two copies of each control's state.** Engines are shared, but properties, setters, change handling and semantics are written twice: `SkUiLabel.cs` is 885 lines and `SkUiCoreLabel.cs` is 974. Every new control pays this twice, and parity depends on tests alone. A source generator that emits the bindable property, the fluent setter and the Core twin's setter from one declaration would remove most of it. (Decided after 1.18: no generator; a parity test over every twin pair instead, [D3](ImplementationPlan-PerformanceAndControls.md#decisions).)
2. **The look is one class that knows every control.** `SkUiLook.cs` is 2,179 lines, and a control's chrome is a member of it. A control in an optional package cannot add a member, so the Markdown package carries its own style object. Charts, Lottie and a data grid need a decided pattern.
3. **Verification debt.** The roadmap lists about twelve open device areas (screen readers, keyboards, Windows, real-device gestures) while features ship daily. A release gate that closes one verification item per new feature would stop the list growing.
4. **Large coordinating classes.** `SkUiViewHandler.cs` (2,603 lines), `SkUiTextFieldModel.cs` (2,644) and `SkUiVirtualVerticalStackLayoutBase.cs` (1,715) concentrate platform and state logic. They are tested, but each is a place where two parallel work packages conflict.

### Risks the roadmap already covers

- Recording runs on the UI thread, so the first frame of a large tree is bounded by it (310 to 360 ms for 400 SkUi\* cards on the S9).
- The surface root is the only relayout boundary.
- Windows composites on the UI thread and can flash on a swap chain resize.
- Drawn popups cannot cover hosted native controls until overlay masks exist.
- Text shadows are rasterized on the CPU, and dashed strokes of complex paths cost 20 ms per frame on the S9.
- Core nodes copy scheme colors when created, so a dark-mode switch misses existing Core trees.

## Implementation review

The steady state is clean: a scroll or a render-thread animation records nothing, so the UI thread has no per-frame work to allocate for. The allocations that remain sit on three paths: input events, frames that re-record, and first frames of large trees. Line numbers are from 1.12.0.

| ID | Where | What happened at 1.12.0 | Fix | Confirm with |
| --- | --- | --- | --- | --- |
| A1 | `SkUiCompositor.cs:115-116`, `SkUiFrameRenderer.cs:21`, `SkUiMetalSurface.cs:592,703`, `SkUiImageCache.cs:175`, `SkUiImageLoader.cs:102`, `SkUiImageDiskCache.cs:15`, `SkUiFonts.cs:13`, `SkUiFrameTrace.cs:41` | 10 gates are `object` fields taken with `lock`; only `SkUiStrokedOutlines` and `SkUiImageSlot` use `System.Threading.Lock` | Change the field type to `Lock`. The commit and render locks are taken every frame on two threads | Suite green; no bench phase slower |
| A2 | `SkUiPointerRouter.cs:155,215,378,701,731`, `SkUiGestureRecognizer.cs:127-158`, `SkUiMauiTaps.cs:66`, `SkUiScrollView.cs:322,494` | `Members.ToArray()` copies the arena's members on every pointer move, press and release | Iterate a pooled snapshot | An allocation test: 100 moves on one pointer allocate 0 bytes |
| A3 | `SkUiRenderRecorder.cs:21,60-111`, `SkUiCompositor.cs:56,77` | A `SkUiRenderBatch` per frame and a `SkUiRenderUpdate` per dirty node are new objects; `GetRange(...).ToArray()` copies a child list twice | Return applied batches and updates to the UI thread and reuse them; one copy through `CollectionsMarshal.AsSpan` | A UI-clock animation scenario with `--quiet-gc`; allocated KB per frame |
| A4 | `SkUiLook.cs` (12 sites), `DefaultSkUiLook.cs:794,962`, `SkUiCoreTable.cs:300,372`, `SkUiButtonFill.cs:46`, `SkUiSliderInput.cs:85`, `SkUiBorderGeometry.cs:98` | `using var paint = new SKPaint` per draw: a managed wrapper, a native object and two P/Invokes each time a control records. Other painters already cache one | One thread-static scratch paint per painter family, `Reset()` before use | `core-stress-buttons`, `skui-stress-buttons` record time and allocated KB |
| A5 | `SkUiShaping.cs:184-193,349-361` | `IsPlain` calls `HasGlyph` per character, which does a `ConcurrentDictionary.GetOrAdd` per character before reading the coverage table | Fetch the coverage array once per string; reject non-simple text first with a vectorized pass | `core-labels`, `skui-labels` measure phase |
| A6 | `SkUiImageLoader.cs:158-190` | A memory-cache hit still builds a `SkUiImageLoadContext` and returns `Task.FromResult` | Check the cache first; `ValueTask` on the internal path | A recycled list of cached images: allocated KB per bound row |
| A7 | `SkUiShape.cs:103`, `SkUiShapes.cs:162`, `SkUiBorder.cs:119`, `SkUiImage.cs:322` and their Core twins | 14 public `params T[]` setters allocate an array per call and then copy it | Add `params ReadOnlySpan<T>` overloads | API comparison reports additions only |

What needed no change: the compositor's ordering (`stackalloc` with an `ArrayPool` fallback), 117 `readonly struct` and 104 `record struct` declarations with 256 `in` parameters, 120 `static` lambdas, no LINQ in rendering, layout or text, `Stopwatch.GetTimestamp` for frames and animations, and allocation tests in `PerformanceTests.cs`.

## .NET 10 / 11 and C# 14 / 15 audit

Not every available feature is used, and most of the unused ones would not help. Six are worth adopting; C# 15 is not among them. Counts are pattern matches across the four library projects. No `LangVersion` is set, so net10 targets compile as C# 14 and net11 targets as C# 15 from the same source.

### Language features

| Feature | Since | Use at 1.12.0 | Verdict |
| --- | --- | --- | --- |
| `field` keyword | C# 14 | 144 sites in 43 files | In use |
| First-class span conversions | C# 14 | Automatic where spans are passed | Nothing to do |
| Extension members, null-conditional assignment | C# 14 | 0 | Style only, no runtime effect |
| User-defined compound assignment | C# 14 | 0 | No large mutable value types to benefit |
| Collection expressions | C# 12 | 291 sites in 100 files | In use |
| Primary constructors | C# 12 | 218 declarations | In use |
| `params ReadOnlySpan<T>` | C# 13 | 0, against 14 `params T[]` setters | Adopt (A7) |
| `lock` on `System.Threading.Lock` | C# 13 | 2 of 12 gates | Adopt (A1) |
| `ref struct`, `allows ref struct`, `scoped` | C# 11 to 13 | 1 `ref struct` | No candidate found |
| Inline arrays | C# 12 | 0 | Skip until a profile shows a fixed small buffer on the heap |
| Collection expression arguments, `with(capacity: n)` | C# 15 | Not usable | Would presize lists, but net10 builds cannot compile it |
| Union types | C# 15 | Not usable | Avoid on hot paths: a generated union boxes value-type cases into one `object?` field, and needs .NET 11 runtime types |
| Closed hierarchies, extension indexers, labeled `break` | C# 15 | Not usable | Readability and exhaustiveness, no performance effect |
| Memory safety rules | C# 15 preview | Not usable | Preview |

Shared source has to stay C# 14 for as long as SDK 10 builds the net10 line by itself (`net10/`). Setting `<LangVersion>14</LangVersion>` in `Directory.Build.props` makes that explicit.

## Proposed features and controls

Ten additions, none on the backlog or the "not planned" list at 1.12.0. Each exists in at least three other toolkits and reuses an engine SkiaUi already has. The roadmap rules out clones of other vendors' controls, so each is the common pattern on SkiaUi's own API. Toolkit names are from memory and were not checked against current vendor documentation. API tables and steps: [the review plan](ImplementationPlan-PerformanceAndControls.md#track-f-features).

| ID | Addition | Other toolkits | Built on | First version |
| --- | --- | --- | --- | --- |
| F1 | `SkUiSegmentedControl`, `SkUiTabView` | iOS `UISegmentedControl`; Material tabs and segmented buttons; Flutter `TabBar`; Syncfusion, Telerik and DevExpress tab views | Toggle transitions, the carousel, `ContentLoading="WhenShown"` | Text and icon segments, a sliding selection, a tab strip over lazily created panes |
| F2 | Scroll-linked effects | Flutter slivers; Android `CoordinatorLayout` and `MotionLayout`; iOS large titles; Syncfusion parallax view | `SkUiRenderLink`, which ties a node's translation to a scroller's offset on the render thread | A public link from a scroller's offset to translation, opacity, scale and a clipped height |
| F3 | `SkUiSheet`: a bottom or side sheet inside the surface | iOS sheet detents; Material bottom sheets; Flutter `DraggableScrollableSheet`; Syncfusion and DevExpress bottom sheets | Scroll controller, dragger, render-thread translation | Detents, drag to dismiss, a scrim, a presenter for the pickers' popups |
| F4 | Charts, in `SkiaUi.Maui.Charts` | Swift Charts; Syncfusion, Telerik and DevExpress charts; Flutter chart packages | Shape painter, text engine, UI-clock transitions | Sparkline, line, area and bar series with axes, a legend and a tooltip |
| F5 | `SkUiChip`, `SkUiChipGroup` | Material chips; Flutter `Chip`, `FilterChip`; Syncfusion, Telerik and DevExpress chips | Button and toggle engines, wrap layout | Action, filter and input chips |
| F6 | `SkUiRangeSlider`, `SkUiRating` | Material and Flutter `RangeSlider`; Syncfusion and Telerik range sliders and ratings | Slider engine and look | Two thumbs with a minimum gap; a rating with half steps |
| F7 | `SkUiAutoComplete` | Material exposed dropdown; Flutter `Autocomplete`; Syncfusion, Telerik and DevExpress autocomplete and combo boxes | Drawn entry, the picker popup contract of 1.12, spans | Suggestions from a list or an async provider, matched text highlighted |
| F8 | Lottie, in `SkiaUi.Maui.Lottie` | Lottie on iOS, Android and Flutter; SkiaSharp's own Lottie view | `SkUiRenderDrawable` | Play, loop, progress, reduce motion; drawn on the render thread |
| F9 | `SkUiDataGrid` | Syncfusion, Telerik and DevExpress data grids; Flutter `DataTable` | Virtual stack, Core table painting, grid splitters | Virtualized rows, sorting, column resize, frozen header and columns |
| F10 | Backdrop blur | iOS `UIVisualEffectView`; Flutter `BackdropFilter`; Android `RenderEffect` | A composite-time property | A blurred, tinted backdrop behind a view |

Why this order: F1, F5 and F6 are cheap and asked for in almost every app. F2 and F3 are motion native MAUI cannot do smoothly, on engines that exist. F4 is the largest single gap. F9 is large and depends on backlog items of the virtual stack. F10 is last for its cost: a backdrop filter re-reads the frame behind it every frame.

Considered and left out: a tree view (after the data grid, on the same row virtualization), shared-element transitions (they need navigation, which SkiaUi leaves to the app), a snackbar (can be folded into the sheet), a staggered grid layout, a signature pad, a barcode generator, and a scheduler, PDF viewer or rich text editor (each a product of its own).
