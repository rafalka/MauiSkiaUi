## Next

Ordered for adoption by real apps (replace a MAUI page's tree with one drawn surface): **full MAUI parity of the controls that already ship comes first**, so a MAUI page ports by changing the XAML prefix instead of rewriting it; then containers for page shells, virtualized lists, list chrome, the carousel and pickers, drawn text input (with the controls built on it, such as the stepper), SVG images and a calendar. Within a phase, the order is the suggested order. Platform looks (phase L) run alongside: each new control ships in the default look, and its platform shapes join the platform looks.

Phase 0 (state-change animations, FR-26) is shipped: looks draw from continuous parameters, transitions run on the UI clock re-recording one control per frame. New controls with state visuals follow the same pattern (a paint struct with the transition, a `SkUiTransitionKind`, the shared animators). Left open: several ripples at once, press scale, render-thread painters.

### Phase P — MAUI parity of shipped controls

Every shipped control gets the MAUI API it is missing. P1–P10 and P11a are shipped (see **Shipped**); P11b is open. Most controls are still partial: they draw and behave like their MAUI counterpart for the common properties, but miss secondary API that real pages use (renamed state properties, text styling, image sources, brushes, shape geometry, scrollbars, accessibility).

**Parity rules:**
- **Performance and architecture come before literal parity.** MAUI parity is the goal, but not at the cost of SkiaUi's performance or architecture. When a MAUI (or toolkit) API works against them (UI-thread animation callbacks, per-frame bindable property churn, native-view assumptions), ship the SkiaUi-shaped equivalent instead and give a short, mechanical conversion path in [Migration.md](../Migration.md) and the migration skills (`plugins/skiaui-migration`), so a person or an agent converts the code without redesigning it. Keep the MAUI shape when it is cheap and harmless (an `int CornerRadius` next to `CornerRadii`, an extra overload that forwards). Example: `SkUiStateContainer.ChangeStateWithAnimation` takes render-thread `SkUiViewAnimation`s instead of MAUI `Animation`s, which tick on the UI thread; the conversion is one line per animated property.
- **MAUI names and signatures win.** Where SkiaUi diverged (`IsChecked` on Switch, `EventHandler<bool>` for `CheckedChanged`, `StrokeWidth` on shapes), the MAUI member is added and the SkiaUi one is renamed or removed before 1.0, marked **Breaking** in the changelog. SkiaUi extensions stay (`CheckState` / `IsThreeState`, vertical `Slider`, `IsIndeterminate`, label chrome, `ShowsPressEffect`).
- **Both layers.** A property lands on the SkUi* control and on its Core twin through the shared engine or painter (fluent `Set*` + CLR property on Core; no attached-property XAML there). Core-only drift found on the way is fixed in the same item (N13).
- **Drawn by the look.** New visuals (scrollbars, decorations, shadows, radio content) get `SkUiLook` entry points and paint structs, as in **Suggested order for a new control**.
- **Checked against MAUI.** Each item adds a XAML parity test: the control's samples from the MAUI docs, with only the namespace prefix changed, load, bind and measure as documented.

#### Popups through the app's popup system

SkiaUi does not replace navigation, so it ships no pages and no popup windows of its own. A drawn control that needs a popup (the pickers; later editable combo boxes, menus) asks the app's popup system through one abstraction, `ISkUiPopupPresenter`, which the app implements on whatever it uses: MAUI's built-in UI, CommunityToolkit's `Popup`, another popup library, a picker UI of its own, its own overlay.

- **Request.** `ShowAsync(SkUiPopupRequest, CancellationToken)`. The request carries:
  - `Anchor`: the MAUI `View` that opens the popup (the drawn picker; for Core, its `SkUiCoreHost`), from which the presenter finds the window (`Anchor.Window`) and the page to show on.
  - `PlatformAnchor`: the nearest ancestor with a platform view (the surface root). Drawn views have no handler, so presenters that place a popup relative to a view use this one with an offset.
  - `AnchorBounds`: the anchor's rectangle in window coordinates, and relative to `PlatformAnchor`, computed by SkiaUi through drawn offsets, transforms, scrolling and clips (as the semantics tree computes accessibility bounds), with the window's safe area.
  - `Placement`: `Anchored` (below the anchor, above when it fits better, start-aligned and mirrored in RTL, at least the anchor's width), `Window` (aligned in the window by `HorizontalOptions` / `VerticalOptions`: a centered dialog or a bottom sheet) or `Absolute` (a window rectangle from the app). The space on each side of the anchor is precomputed, so a presenter flips without measuring.
  - Size: `PreferredSize` (the content measured), `MaximumSize` (the window's safe area minus margins, `MaxPopupHeight`).
  - `Content`: a ready MAUI `View`, a drawn surface (`SkUiContentView`) with the list, which any popup system hosts like any other view. A presenter that shows its own UI instead reads the typed request (`SkUiListPopupRequest`: item texts, selected index, title) and completes it with its choice.
- **Lifetime.** `ShowAsync` completes when the popup is gone. The content completes the request with a result (an item chosen); the presenter completes it with none when the user dismisses it (a tap outside, Back, Escape); the control cancels the token when the popup must close (`IsOpen = false`, the picker unfocused, disabled, hidden or removed, the anchor scrolled or the window resized). One popup per control; the request, its content and the presenter keep no reference to the control after completion.
- **Registration.** App-wide (`SkUiPopups.Presenter`, also settable from `UseSkiaUi(options => options.PopupPresenter = …)`), overridable per control (`PopupPresenter`). With none registered, pickers fall back to MAUI's own `DisplayActionSheetAsync` on the anchor's page (`SkUiActionSheetPopupPresenter`: centered, plain item texts; MAUI's UI, not SkiaUi's) and write one `Trace` line (decided in C6).
- **As built (C6).** The token passed to `ShowAsync` is the request's `CloseRequested`: the content's choice (`Complete`) and the control's close both cancel it, so a presenter has one rule (close on cancellation). The request holds the anchor, surface, page and window weakly and drops the content when it completes; a picker also closes its popup when its surface is torn down, so a presenter's popup still open after its page went keeps nothing alive. Presenters shown in the docs: CommunityToolkit (compiled, in the samples app and the demo), MAUI's action sheet (built in), a popup control of the app's (a sketch), a navigation service of the app's with a popup stack (open, close, bring to front).
- **Presenters are not in the library.** The library takes no popup dependency. Integrations ship as their own packages (below); other presenters are shown in the docs. The samples app and the control docs carry presenters for MAUI's action sheet, CommunityToolkit's `Popup` (the content placed in the toolkit's overlay by alignment and margins, since toolkit v2 has no anchor); [Migration.md](../Migration.md) and the migration skills show how to plug in the app's own.
- **Native over drawn.** The popup is a window-level platform view of the app's popup system, so it covers hosted native controls without overlay masks.

### Phase D — Drawn text input (FR-16, amended)

`SkUiEntry` and `SkUiEditor` are drawn by SkiaUi; the platform keyboard and IME talk to them through a proxy. Hosting stays for controls that need a platform engine (WebView, maps, media), and `SkUiMauiContentView` stays as the fallback for native text fields.

**Why:** hosted text fields are the most common native overlay on real pages, and overlays bring every hosting limit: snapshots while scrolling, rectangle-only clips, no drawn content on top (popups, sheets), no transforms or opacity from ancestors, one platform view per cell in lists (Phase B), no Core-layer use, and the A6 regression surface. Drawn input removes all of these for text. It also unlocks controls built on editable text: SearchBar, the stepper (D7), editable combo boxes, and inline editing in collection cells.

**Rules:**
- **Platform services stay native.** The OS still owns the keyboard, IME composition, autocorrect, dictation, the clipboard and the edit menu. SkiaUi owns text, caret, selection, layout and drawing, and drives the native services through the proxy.
- **One engine, both layers.** The editing model and the drawing are layer-agnostic (N13); `SkUiEntry` / `SkUiEditor` and `SkUiCoreEntry` / `SkUiCoreEditor` are thin facades over them, and the look draws the chrome.
- **MAUI's API.** `Entry` / `Editor` members by name (`Text`, `Placeholder`, `Keyboard`, `ReturnType`, `Completed`, `CursorPosition`, `SelectionLength`, …), so a XAML port changes only the prefix instead of adding `SkUiMauiContentView` around the field.

### Phase E — SVG images (later)

An SVG added as a `MauiImage` already works: Resizetizer turns it into density PNGs at build time and P4 loads those. ### Phase F — Calendar (`SkUiCalendar`)

A drawn calendar: a control of its own on a page (bookings, schedules, a date range) and the month grid the date picker's popup shows instead of wheels (Android's and Windows' date dialogs). Formerly C7b; requirements in [FR-33](Requirements.md#fr-33--calendar). MAUI has no calendar, so the API is SkiaUi's own (MAUI's names where the date picker already has them: `MinimumDate` / `MaximumDate`), and a conversion path from both in [Migration.md](../Migration.md) and the migration skills. Both layers (`SkUiCalendar`, `SkUiCoreCalendar`) on one engine, and on C7's date rules, so the picker and the calendar agree about which days can be chosen.

**Rules:**
- **A month is one drawn node, not 42 views.** Day cells are laid out, hit-tested and drawn by the calendar (a recording per month, recycled while swiping), as the indicator view draws its dots. Per-day views are the slow path; the fast one is a per-day style callback the recording reads.
- **Navigation on the render thread.** Swiping between months reuses the carousel's snapping scroll engine (C4: virtual pages, flings, keyboard steps), so a swipe records nothing new once the neighbors are recorded.
- **Drawn by the look.** Header, navigation buttons, day names, cells, today, selection and range band through `SkUiLook` paint structs (as **Suggested order for a new control**); colors from the color scheme. Platform looks draw their platform's calendar (Material's date picker, Fluent's `CalendarView`, UIKit's `UICalendarView`) in L3.

### Architecture work alongside

From [ArchitectureReview.md](ArchitectureReview.md) (finding numbers N\*). Scheduled next to the phases above, not after them.

- **Now (small, correctness):** disabled controls must not block ancestor scrolling (N2); Core `IsEnabled` / `InputTransparent` with one blocking rule (N3); child alignment in every Core container (N4); scheme defaults resolved at paint time instead of snapshotted at construction (rest of N6; look / scheme swaps already redraw live surfaces).
- **With Phase A:** measure invalidation without re-recording ancestors (N5): shipped for SkUi* views with A5 (the expander relayouts every animation frame); open for Core nodes, with the early-out at measure-dirty parents.
- **Before Phase B:** relayout boundaries; raster cache of stable subtrees (N7). The shared image cache (N9) shipped with P4; fling live extents (N11) shipped with P8.

## Cross-cutting

| Topic | Expectation |
| --- | --- |
| Correctness → optimize | NFR-2 on every new hot path |
| Both layers | New controls ship on SkUi* and Core with the same look entry points |
| Extensibility | Looks draw every control; virtual hooks / interfaces / shared helpers (NFR-4) |
| Testing | Headless tests by functionality ([Testing.md](Testing.md)); a leak scenario for every new stateful control; demo page per control (enforced by `ComponentDemoTests`) |
| Trimming / AOT | No reflection; analyzers fail the build |
| Tracking | Check off [Requirements.md](Requirements.md); summarize shipped behavior in [Development.md](../../Development.md); changelog under `## Unreleased` |

## Suggested order for a new control

1. Look entry point (`SkUiLook.Draw*` / `Measure*`, paint struct carrying the transition state, `SkUiTransitionKind` if it has state visuals, default look)
2. Types on both layers, shared math / input helpers
3. Measure / arrange, paint
4. Input through the gesture arena (write user changes back to bindables)
5. Animation: state changes through the shared transition animators; continuous motion on the render thread when possible
6. Demo page, docs page under [docs/controls/](../controls/README.md)
7. Tests, leak scenario, then optimize
